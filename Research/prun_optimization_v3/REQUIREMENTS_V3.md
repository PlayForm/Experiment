# PRUN-APE/3 — Extended Requirements Contract

**Status:** Draft. Every `MUST` is a proposed acceptance condition, not a claim
it has been implemented. Inherits all requirements and non-goals from v2 without
deleting or weakening them. Terminology: coordinator (deterministic Rust control
service), director (parent reasoning agent), patcher (scoped coding agent),
novelty gate (deterministic comparator), oracle (trusted correctness), benchmark
runner (trusted measurement executor), evidence capsule (signed redacted results
summary).

## A. Non-negotiable invariants

- **INV-001** Authoritative facts are generated by deterministic tools and
  committed as immutable evidence; agents are hypothesis generators, not truth
  or policy authorities.
- **INV-002** A worker may receive the minimum task-specific source and evidence
  required to act, not all accessible laboratory data. Data access is enforced
  by broker/API/storage capabilities, not by prompt instructions alone.
- **INV-003** The benchmark runner does not accept or execute arbitrary
  agent-supplied fixture changes, oracle code, benchmark flags or network
  endpoints; only an approved signed run manifest.
- **INV-004** A candidate has both a frozen absolute baseline and a direct
  parent, with separate comparison evidence. Multi-parent integration results
  must be measured anew.
- **INV-005** No durable fact is stored _only_ in a conversation, prompt or OTel
  span. Stateful tasks can replay after coordinator crash and loss of all LLM
  sessions.
- **INV-006** Every identity, cache hit, similarity verdict, signed stamp,
  comparison and release action is scoped to immutable source, build, workload,
  measurement protocol and hardware context.
- **INV-007** Raw sample truth and continuous control telemetry are separate:
  loss of an OTel span never mutates or fabricates timing evidence.
- **INV-008** No trace-enabled product timing trial contributes to a
  trace-disabled release leaderboard without explicit separate comparison
  policy.
- **INV-009** Runtime behavior-preservation takes precedence over a speedup;
  failures exit without promotion and enter audit history.
- **INV-010** Rejected and inconclusive experiments are discoverable, with
  reason, and cannot be rewritten as untested duplicate wins.

## B. Agent fleet and recursive experimental cycle

- **AGT3-001** A warm agent pool exists; idle workers consume no benchmark CPU
  and accept leases only from the coordinator.
- **AGT3-002** Five-way fanout is configurable; each candidate shares identical
  baseline code, workload protocol, oracle, hardware cohort and generation ID.
- **AGT3-003** Agent job assignment includes role policy version, context view
  checksum, exact Git parent/source snapshot, mutation scope, allowed tools,
  attempt budget, expiration time and structured output schema.
- **AGT3-004** The patcher must create a saved code diff and immutable committed
  source snapshot before submission; natural-language ideas alone cannot enter
  build/benchmark.
- **AGT3-005** In-flight worktrees are isolated; no agent has writable access to
  peers or production source.
- **AGT3-006** Benchmark result path: runner -> coordinator ingestion ->
  integrity check -> deterministic evaluator -> signed feedback capsule ->
  assigned patcher. No runner-to-patcher channel.
- **AGT3-007** Each feedback-driven revision produces a new mutation ID and
  parent link. Earlier patch and tests remain immutable.
- **AGT3-008** The coordinator may pause, resume, evict/restart or replace a
  worker from the durable transcript/task ledger; no correctness decision
  depends on lost LLM context.
- **AGT3-009** A patcher may not read sealed holdout, other agents' raw drafts
  or unrestricted leaderboard while actively submitting candidates.
- **AGT3-010** Director receives evidence-backed generation summaries and can
  request research changes, never mutate raw samples.
- **AGT3-011** Retry and duplicate job messages have idempotency keys; multiple
  workers cannot double-submit the same accepted mutation state.
- **AGT3-012** Human-controlled release approval remains required by default;
  unattended mutation exploration is bounded.

## C. Identity, novelty, feature compatibility and evidence reuse

- **NOV-001** Source snapshot, patch, binary, build recipe, runtime policy,
  fixture, protocol and environment each have separate content hashes/identity
  versions.
- **NOV-002** Exact duplicate patch detection runs before expensive compilation
  or inference when possible; all gate decisions record algorithms and candidate
  hashes.
- **NOV-003** Structural similarity checks changed code symbols, canonicalized
  syntax, touched paths, compiler features and parent ancestry. Similarity is
  probabilistic/advisory, not proof of semantic equivalence.
- **NOV-004** Hypothesis similarity supports nearest-neighbor lookup over
  structured mechanism taxonomy; optional model/embedding must have a versioned
  policy and provenance.
- **NOV-005** Compile-time features, runtime strategy groups and mechanism
  identity are different namespaces. Conflict checks must distinguish
  coexistence, active-selection exclusivity and suspected interactions.
- **NOV-006** Reused build/results must share the exact declared key and
  comparable environment. Otherwise prior evidence is displayed as reference,
  not silently reused as a new trial.
- **NOV-007** Near-duplicate contested decisions are appealable with evidence;
  manual override is recorded and policy-scoped.
- **NOV-008** Fingerprint algorithms and lookup indexes are rebuildable from
  immutable records.
- **NOV-009** Already-tested failures remain searchable to prevent repeated
  agent exploration, without forcing permanent exclusion of genuinely distinct
  hardware/workloads.
- **NOV-010** All five fanout proposals must be searchable by generation,
  including dropped, exact-hit and invalid proposals.

## D. Prompt lifecycle and reduction of communication latency

- **CTX-001** Every system/developer/user pre-prompt and subsequent feedback
  prompt has stable template ID/version/hash, resolved instance digest and
  authorized context digest.
- **CTX-002** Store model identity, model revision when exposed, sampling
  parameters, tools, usage, TTFT, TTFB, output token throughput, tool-call round
  trips and finish reason.
- **CTX-003** Capture each tool request/result, stream checkpoint, retry,
  compaction and conversation link with immutable turn sequence and privacy
  classification.
- **CTX-004** Compactions point to source-turn IDs and preserve original
  evidence according to retention policy; no unrecorded context loss.
- **CTX-005** The coordinator must support short feedback capsules with summary
  statistics, own-lineage details, evidence IDs and no unnecessary raw logs.
- **CTX-006** Cache prompt/source bundles and avoid unnecessary inference for
  exact duplicate submissions.
- **CTX-007** Pre-run context validation rejects unauthorized source or holdout
  references without relying on model instruction-following.
- **CTX-008** Agent configurations may diversify research constraints, but
  prompt/model variation is recorded to measure duplicate rates and efficiency
  objectively.
- **CTX-009** Shared model provider state may not be assumed independent across
  tasks. Cross-lane hidden information leakage must be treated as an evaluation
  risk.
- **CTX-010** Token-side speed and benchmark-side performance are separate
  metrics with no common scalar champion unless an explicitly declared weighted
  operations policy exists.

## E. Two-plane OpenTelemetry and measurement truth

- **TEL-001** Distinct `lab.control` and `prun.product` service namespaces with
  independent sampler/retention rules and no accidental high-cardinality metric
  attributes.
- **TEL-002** Control plane records task, message, tool, token, queue, container
  lifecycle and analysis spans/events with async span links.
- **TEL-003** Product diagnostic plane can measure parse, plan, walk, match,
  schedule, spawn, wait, output, shutdown, allocator and system counters where
  supported.
- **TEL-004** Define binary variants `trace-off`, `trace-lite`,
  `trace-diagnostic`, `profile-build`; hash and label all builds and stop
  cross-mode comparison contamination.
- **TEL-005** Default primary Hyperfine release trials use `trace-off` and do
  not export product spans from their measured processes.
- **TEL-006** Diagnostic tracing is performed in separate executions, on an
  appropriate host/window, and explicitly labeled non-primary.
- **TEL-007** Retain immutable timings and event ledger even when trace storage
  is sampled, dropped, over budget or offline.
- **TEL-008** All agent/experiment cross-plane links are immutable IDs and span
  links, not a single multi-day parent span.
- **TEL-009** Observe the telemetry pipeline itself: exporter errors, queue
  depth, receiver limits, dropped spans and index lag.
- **TEL-010** Maintain per-mode instrumentation overhead studies that quantify
  trace-lite versus trace-off differences by workload/hardware cohort.
- **TEL-011** A strict Rust-only backend can use `opentelemetry-proto` with
  `axum`/`tonic` for OTLP intake; an off-the-shelf Collector is explicitly
  optional and non-Rust.
- **TEL-012** PII/user-command/path payloads are excluded from spans by default,
  with opt-in redaction and retention controls.

## F. Scheduler, correctness, performance and evidence lifecycle

- **EXP-001** Only trusted scheduler can grant exclusive benchmark leases;
  cpuset overlaps, core siblings and shared resource interference are assessed.
- **EXP-002** Builds, model inference and dashboard rendering never compete on
  the reserved benchmark resources during precision trials.
- **EXP-003** Candidate-first smoke/oracle validation runs before the expensive
  benchmark queue.
- **EXP-004** Every primary trial stores exact command spec,
  binary/fixture/host/protocol hashes, warmed state, order seed, raw samples and
  environment health.
- **EXP-005** Comparisons distinguish full end-to-end wall time, marginal
  mutation improvement, fixed B0 improvement and diagnostic stage findings.
- **EXP-006** A candidate cannot redefine the oracle, performance unit, fixture
  or comparator inside its own mutation without separate approval.
- **EXP-007** Every result gets an integrity verdict (`valid`, `contaminated`,
  `incomplete`, `quarantined`), with raw data retained even when invalid.
- **EXP-008** Holdout samples do not flow into adaptive search; confirmation is
  at predetermined gates, with failure disclosures minimized.
- **EXP-009** Decisions use predeclared practical gains, statistical
  uncertainty, regression guardrails and multiple-attempt context.
- **EXP-010** Signed attestations for scope, novelty, oracle, benchmark
  integrity, analysis, integration and release approvals are independently
  scoped.
- **EXP-011** All failure and restart paths have bounded retry, heartbeat, lease
  reclamation and reconstructable status.
- **EXP-012** A week's campaign is pause/resume/reboot-resilient,
  resource-budgeted, audit-ready and never automatically publishes a binary
  without authorization.

## G. Storage, API, dashboard and privacy

- **DAT-001** Event log is authoritative and append-only; source, binaries,
  profiles, prompts, raw samples and comparisons are CAS objects.
- **DAT-002** Agent views are filtered server-side and audited. Dashboard's
  read-only views do not grant file-system level DB/CAS access.
- **DAT-003** Separate data classifications and retention rules for source, raw
  commands, provider conversations, telemetry and sealed holdout artifacts.
- **DAT-004** A `reproduce <experiment_id>` action resolves pinned source,
  image, binary, fixture, measurements and protocol and reports missing
  dependencies explicitly.
- **DAT-005** Cross-host event correlation records monotonic durations
  separately from wall clocks and clock uncertainty.
- **DAT-006** Dashboard has two clock-domain boards, a correlation spine, full
  agent/prompt history, lineage graph, comparison microscope and authorized
  control actions.
- **DAT-007** UI connections support cursor resume, snapshot bootstrap and
  missing-event detection; UI never serves as primary storage.
- **DAT-008** Every UI action is authenticated, permission-checked, idempotent,
  appended as audit event and subject to policy/human gate.
- **DAT-009** UI may use GPUI and Ely GPUI with optional `gpui-wry`, pinned
  dependency commits, per-platform tests and no privileged WebView IPC.
- **DAT-010** An offline local installation can run without a cloud telemetry
  backend; model inference may be local or explicitly connected to an external
  provider.

## H. Acceptance phases

- **A0 Evidence substrate:** after hard-kill/restart, ledger reconstructs tasks,
  outputs and leases with no double decisions.
- **A1 One patcher:** real scoped agent writes patch, novelty gate accepts,
  builder runs, oracle validates, runner measures, feedback returns to same
  logical conversation, with all hashes.
- **A2 Five-way fanout:** five independent patches from one frozen baseline,
  duplicate cache effectiveness recorded, benchmark exclusion enforced, stable
  results recovered after process crashes.
- **A3 Anti-contamination:** simulated attempt to edit oracle, read sibling
  worktree, access sealed holdout, forge a result or promote its own patch is
  denied and logged.
- **A4 Product telemetry:** stage instrumentation produces diagnostic traces;
  `trace-off` benchmark outputs no product OTLP export; measured overhead
  explicitly reported.
- **A5 Control telemetry:** every task/queue/LLM/tool step appears in the
  control signal plane; reconstruction from event ledger works even when spans
  are deliberately dropped.
- **A6 Dashboard:** one Rust GPUI desktop view can map any plotted point to its
  committed patch, source/binary digest, exact trial and prompt lineage.
- **A7 Seven-day soak:** budget limits, recovery, partial failure, stale lease
  reclamation, CAS integrity and complete failure audit survive a configured
  long-running campaign; speedups must be independently confirmed, not assumed.
